\section{Purpose}

This document defines the design, implementation, testing, and review
requirements for software written in C and Python.

The objectives are:

\begin{itemize}
    \item correctness;
    \item safety;
    \item readability;
    \item maintainability;
    \item portability;
    \item testability;
    \item predictable resource usage;
    \item support for static analysis and code review.
\end{itemize}

\section{Scope}

This standard applies to:

\begin{itemize}
    \item production C source code;
    \item production Python source code;
    \item unit tests and integration tests;
    \item build scripts and automation;
    \item public interfaces and internal modules;
    \item documentation and code review.
\end{itemize}

Generated code, third-party code, and legacy code may be exempted,
but each exemption shall be documented.

\section{Normative Language}

The terms \textbf{MUST}, \textbf{MUST NOT}, \textbf{SHOULD},
\textbf{SHOULD NOT}, and \textbf{MAY} are normative.

\begin{description}
    \item[MUST] An absolute requirement.
    \item[SHOULD] A recommendation that may be overridden with justification.
    \item[MAY] An optional practice.
\end{description}

\section{Standards and References}

This project is based on the following sources:

\begin{itemize}
    \item NASA/JPL ``Power of 10'' rules for safety-critical C;
    \item Scilab C programming conventions;
    \item MaJerle C coding style;
    \item Essential C coding standards from BestHub;
    \item PEP 8;
    \item Black, Ruff, isort, and mypy conventions for Python.
\end{itemize}

Where these sources conflict, this document takes precedence.

\section{Project Rule Precedence}

The following precedence order shall be used:

\begin{enumerate}
    \item safety and system requirements;
    \item project architecture and interface requirements;
    \item NASA/JPL safety rules for applicable C code;
    \item C11 and Python language requirements;
    \item formatting and naming rules;
    \item local implementation preferences.
\end{enumerate}

Any deviation from a mandatory rule requires a documented exception.

\section{General Design Principles}

\begin{itemize}
    \item Each module shall have one clearly defined responsibility.
    \item Interfaces shall be explicit and minimal.
    \item Mutable global state shall be avoided.
    \item Functions shall perform one primary task.
    \item Resource ownership shall be documented.
    \item Error conditions shall be handled explicitly.
    \item Correctness shall be established before optimization.
    \item Code shall be easy to test independently.
    \item Complexity shall be kept low enough for human review.
\end{itemize}

\section{C Coding Standard}

\subsection{Language Version}

New C code shall use C11 unless the target platform requires an
earlier standard.

The compiler shall operate in a strict conformance mode where practical.

\subsection{Formatting}

\begin{itemize}
    \item Four spaces shall be used for indentation.
    \item Tabs shall not be used.
    \item Lines shall not contain trailing whitespace.
    \item Braces shall always be used, including for single statements.
    \item A consistent brace style shall be used throughout the project.
    \item The project shall use one formatter configuration.
\end{itemize}

This project adopts same-line braces because they are compatible with the
selected MaJerle style and common automated formatting tools.

\begin{lstlisting}[language=C]
if (condition) {
    perform_action();
} else {
    perform_alternative();
}
\end{lstlisting}

\subsection{Naming}

\begin{itemize}
    \item Functions and variables shall use lowercase snake case.
    \item Types shall use lowercase snake case with a project-approved suffix.
    \item Constants and macros shall use uppercase snake case.
    \item Names shall describe their purpose.
    \item Reserved identifiers beginning with double underscores shall not be used.
    \item Single-letter names shall be avoided except for short local indices.
\end{itemize}

\begin{lstlisting}[language=C]
uint32_t packet_length;
static int32_t calculate_checksum(void);
#define MAX_PACKET_LENGTH 1024
\end{lstlisting}

\subsection{Functions}

\begin{itemize}
    \item Functions shall perform one logical task.
    \item Functions should normally contain no more than 50--60 lines.
    \item Function nesting should not exceed four levels.
    \item Internal functions shall be declared \texttt{static}.
    \item Functions with no parameters shall use \texttt{(void)}.
    \item Public functions shall have declarations in a header file.
    \item Parameters shall be validated by the called function.
    \item Return values shall be checked by the calling function.
    \item Function contracts shall be documented using Doxygen.
\end{itemize}

\begin{lstlisting}[language=C]
/**
 * @brief Calculates the checksum of a byte buffer.
 *
 * @param data Input buffer.
 * @param length Number of bytes in the buffer.
 * @return Calculated checksum.
 */
uint32_t calculate_checksum(const uint8_t *data, size_t length);
\end{lstlisting}

\subsection{NASA/JPL Power of 10 Rules}

For safety-critical C modules:

\begin{enumerate}
    \item Do not use \texttt{goto}, \texttt{setjmp}, or \texttt{longjmp}.
    \item Do not use direct or indirect recursion.
    \item Every loop shall have a statically reviewable upper bound.
    \item Dynamic memory allocation shall not occur after initialization.
    \item Functions shall remain short and reviewable.
    \item Data shall be declared at the smallest practical scope.
    \item Non-void return values shall always be checked.
    \item Function parameters shall be validated.
    \item Preprocessor use shall be limited.
    \item Pointer use shall be restricted and documented.
    \item Function pointers shall not be used unless specifically approved.
    \item Compiler warnings shall be treated as errors.
    \item Static analysis shall produce no unresolved warnings.
    \item Assertions shall be used to detect impossible states.
\end{enumerate}

The original Power of 10 rules were developed for C code where static
analysis, bounded resource use, and reviewability are important. They
should therefore be marked as ``applicable'' or ``not applicable'' for
each module rather than applied blindly to every program. <citation src="1"></citation>

\subsection{Memory Management}

\begin{itemize}
    \item Memory ownership shall be documented.
    \item Every allocation shall have one clearly identified owner.
    \item Every allocated object shall have a defined release path.
    \item Use-after-free and double-free behavior shall be prevented.
    \item Variable-length arrays shall not be used.
    \item Safety-critical modules shall not allocate memory after startup.
    \item Allocation failures shall be handled explicitly.
\end{itemize}

\subsection{Pointers}

\begin{itemize}
    \item Pointers shall be checked before dereferencing unless validity is
          guaranteed by construction.
    \item Pointer depth should normally be limited to one level.
    \item Pointer ownership and lifetime shall be documented.
    \item \texttt{const} shall be used whenever data is not modified.
    \item Pointer arithmetic shall be minimized and reviewed carefully.
\end{itemize}

\subsection{Preprocessor}

\begin{itemize}
    \item Header guards shall be used.
    \item Function-like macros shall be avoided when an inline function is
          practical.
    \item Macro arguments shall be parenthesized.
    \item Multi-statement macros shall use \texttt{do \{ \} while (0)}.
    \item Conditional compilation shall be limited to configuration and
          platform-specific code.
\end{itemize}

\subsection{Headers}

\begin{itemize}
    \item Headers shall contain declarations and interface definitions.
    \item Headers shall not define ordinary global variables.
    \item Headers shall be self-contained.
    \item Unused includes shall be removed.
    \item Circular header dependencies are prohibited.
    \item Standard headers shall use angle brackets.
    \item Project headers shall use quotation marks.
\end{itemize}

\section{Python Coding Standard}

\subsection{Formatting}

\begin{itemize}
    \item Python code shall follow PEP 8.
    \item Four spaces shall be used for indentation.
    \item Tabs shall not be used.
    \item The maximum line length shall be 88 characters.
    \item Black shall be used for formatting.
    \item Ruff shall be used for linting.
    \item isort shall be used for import ordering.
\end{itemize}

\subsection{Naming}

\begin{itemize}
    \item Functions, variables, and modules shall use \texttt{snake\_case}.
    \item Classes shall use \texttt{CamelCase}.
    \item Constants shall use \texttt{UPPER\_CASE}.
    \item Private implementation details may use a leading underscore.
    \item Names shall be descriptive and unambiguous.
\end{itemize}

\subsection{Imports}

Imports shall be grouped in this order:

\begin{enumerate}
    \item standard library;
    \item third-party packages;
    \item local project packages.
\end{enumerate}

Wildcard imports are prohibited.

\begin{lstlisting}[language=Python]
import json
from pathlib import Path

import requests

from project.configuration import Settings
\end{lstlisting}

\subsection{Type Hints}

Public functions shall include type hints for parameters and return values.

\begin{lstlisting}[language=Python]
def calculate_checksum(data: bytes) -> int:
    """Return the checksum for data."""
    return sum(data) % 256
\end{lstlisting}

mypy shall be used for static type checking where practical.

\subsection{Documentation}

Public modules, classes, functions, and methods shall have docstrings.
Google-style docstrings shall be used consistently.

\subsection{Error Handling}

\begin{itemize}
    \item Specific exception types shall be used.
    \item Bare \texttt{except:} clauses are prohibited.
    \item Exceptions shall be handled at the appropriate abstraction level.
    \item Exceptions shall not be silently discarded.
    \item Context managers shall be used for resource management.
\end{itemize}

\begin{lstlisting}[language=Python]
with open(file_path, "r", encoding="utf-8") as input_file:
    contents = input_file.read()
\end{lstlisting}

\subsection{Testing}

\begin{itemize}
    \item Unit tests shall be written for new functionality.
    \item Normal, boundary, and invalid inputs shall be tested.
    \item Tests shall have descriptive names.
    \item External dependencies shall be mocked where appropriate.
    \item Tests shall not depend on execution order.
\end{itemize}

\section{Testing and Verification}

The project shall use the following verification stages:

\begin{enumerate}
    \item formatting;
    \item compilation or syntax checking;
    \item static analysis;
    \item unit testing;
    \item integration testing;
    \item code review;
    \item release validation.
\end{enumerate}

\subsection{C Tooling}

The exact tools shall be selected per target platform, but the minimum
checks should include:

\begin{itemize}
    \item compiler warnings at a strict level;
    \item \texttt{clang-format};
    \item \texttt{clang-tidy} or another static analyzer;
    \item AddressSanitizer where supported;
    \item UndefinedBehaviorSanitizer where supported;
    \item unit-test execution.
\end{itemize}

\subsection{Python Tooling}

The minimum Python checks should include:

\begin{itemize}
    \item Black formatting;
    \item Ruff linting;
    \item mypy type checking;
    \item unit tests using pytest;
    \item coverage measurement where appropriate.
\end{itemize}

\section{Exceptions}

An exception shall contain:

\begin{itemize}
    \item the rule being violated;
    \item the affected file or module;
    \item the technical reason;
    \item the risk introduced;
    \item the mitigation;
    \item the approving reviewer;
    \item an expiration or review date.
\end{itemize}

\section{Code Review Checklist}

Reviewers shall confirm:

\begin{itemize}
    \item requirements are traceable to implementation;
    \item interfaces are clearly defined;
    \item errors are handled;
    \item resources are released correctly;
    \item boundaries and invalid inputs are tested;
    \item compiler and static-analysis warnings are resolved;
    \item NASA rules are satisfied for applicable C modules;
    \item formatting tools produce no changes;
    \item documentation is accurate;
    \item the change is appropriately scoped.
\end{itemize}
